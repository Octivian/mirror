# 烘焙 × 茶饮 垂类情报台

一个自包含的静态情报站 + 一条可运行的抓取链。双击 `index.html` 就能看，不依赖网络、不依赖任何 CDN。

## 目录

```
情报平台/
├── index.html      ← 成品。数据已内嵌，可直接打开/发送/托管
├── template.html   ← 页面骨架（不含数据），改样式改这里
├── build.py        ← 把 data/*.json 注入模板，生成 index.html
├── fetch.py        ← 抓可自动化的信源，产出待审草稿
└── data/
    ├── feed.json     ← 情报流（主数据，人工/AI 维护）
    ├── brands.json   ← 品牌档案
    ├── sources.json  ← 信源分层 + 可抓取性矩阵
    └── draft.json    ← fetch.py 的产物（待审，不直接上线）
```

## 三条命令

```bash
python3 build.py      # 改完 data/ 里的 json 后，重新生成 index.html（带硬校验）
python3 fetch.py      # 抓红餐网等媒体，写 data/draft.json
python3 fetch.py --show   # 只看抓到什么，不落盘
```

`build.py` 会拦下这几类错误：缺 id、id 重复、category 不在枚举里、
**有 date 但 date_precision 写成 unknown 以外的值却没有日期**、count 与实际条数不符。
校验不过就不生成页面，避免把错数据发出去。

## 更新一次情报的完整流程

1. `python3 fetch.py` → 看 `data/draft.json`，媒体侧的新文章在这里
2. 公众号侧靠检索补：搜「品牌名 + 上新/首店/联名」，命中的 `mp.weixin.qq.com` 正文取回来
3. 把可用的条目并入 `data/feed.json`，补齐 `brand_id / category / module / detail / source`
4. `python3 build.py` → 新页面生成
5. `count` 字段跟着条数一起改，否则 build 会报错

## 能力边界（重要，别对外承诺做不到的事）

| 信源 | 能否自动 | 说明 |
|---|---|---|
| 行业媒体（红餐网等） | ✅ 可全自动 | `fetch.py` 已跑通，按品类词过滤后只留相关条目 |
| 品牌公众号 | ⚠️ 需检索命中 | 微信无公开接口；靠搜索命中 `mp.weixin.qq.com` 后取正文，链接带签名有时效 |
| 商场/地方公众号 | ⚠️ 需检索命中 | 首店信息的第一落点，同样走搜索 |
| 小红书 / 抖音 / 大众点评 | ❌ 无接口 | 三家均无公开 API，Cookie 抓取违反协议且极易失效。只标账号，不承诺采集 |
| 企查查 / 窄门餐眼 | ❌ 需人工 | 付费或无接口，用于核验经营主体与门店数 |

**公众号这块的实话**：微信没有给第三方留任何合规的批量读取口子。任何声称能稳定全量抓公众号的方案，
用的都是灰产接口或者随时会死的 Sogou 代理。目前唯一能长期跑的办法是"检索命中 → 取正文 → 人工判相关性"，
也就是让 AI 每周跑一次检索任务，而不是部署一个爬虫。

## 数据诚实约定

- 日期四级：精确到日 / 只知月 / 只知季节 / 原文未标。**不可考的一律显示「日期待核」，不补推测值。**
- 品牌自述数据（战报 GMV 等）标「品牌口径」，不当第三方数据用。
- 加盟招商站的门店数不采信（茶聚场被标 547 家、实际 6 家；可露朵被标 319 家、品牌方口径 14 家）。
- `confidence: medium` 的条目会在卡片上显示「置信中」。
