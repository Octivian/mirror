# 商品销量诊断（product-sales-diagnosis）

把一张商品行级明细表，变成一份能直接拿去开会讨论的「哪些 SKU 该下架」看板。

> **本机运行环境（2026-11-10 安装时补，仅环境适配，不改任何判定规则）**：
> `diagnose.py` 依赖 pandas / numpy / openpyxl。WorkBuddy 默认的 `python3`（3.13）没有这些库，
> 本机 `/usr/bin/python3`（3.9.6）已装齐（pandas 2.3.3 / numpy 2.0.2 / openpyxl 3.1.5）。
> 下方命令一律用 `/usr/bin/python3`，不要直接写 `python3`，否则会报 ModuleNotFoundError。

## 何时用

命中任一即用：

- 用户给出商品明细 / 订单明细，问「哪些商品卖不动了」「哪些该下架」「商品结构怎么样」
- 要求做商品维度的周趋势、动销分析、滞销品清理、货盘精简
- 月报/季报里需要「商品结构」章节的支撑数据
- 用户说「盘一下商品」「商品销量趋势」「SKU 诊断」

不适用：只看整体大盘（用经营复盘类技能）；只想手工对比几个商品。

## 输入要求

**必需**：一张商品行级明细表，每行 = 一个订单里的一件商品，至少包含：

| 字段 | 说明 |
|---|---|
| 商品名称 | 同名不同空格会被自动归一 |
| 数量 | 件数 |
| 金额 | 该行成交金额 |
| 时间 | 付款时间 / 下单时间 / 日期，三者有其一 |

**时间字段的两种来源**：

1. 商品表自带日期列 → 一个文件就够
2. 商品表没有日期列（如部分有赞导出）→ 再给订单表（含订单号 + 付款时间），脚本按订单号关联

**可选字段**：分类（用于分类汇总与节令识别）、单价、订单商品状态（剔退款）、付款方式（用于统计渠道构成）。

**数据跨度**：至少 **2 个月（≥56 天）**。不足时脚本会跑但强提示「判定仅供参考」——规则本身要求 2 个月，短窗口的趋势不可信。

## 🔴 销量口径：全渠道动销（默认，不要改）

**统计这个商品在所有渠道卖出的总件数**：小程序/门店直接购买、储值卡支付、外卖（外部支付）、抖音券与美团券核销、活动兑换与赠品。

**为什么不能按支付方式过滤**：下架决策问的是「这款产品还有没有人买」。同一款蛋糕，通过美团外卖卖出去和顾客到店买，后厨一样要做、原料一样要消耗。如果只统计自有支付，会把大批商品的销量低估一半以上——曾经出过这个错，一款全渠道卖 103 件的蛋糕只被算成 44 件，导致被误判下架。

`--exclude-pay` 默认**为空**（不剔除）。只有明确要看单一渠道时才填，且报告里会标注「非全渠道口径」。

## 执行流程

### 第 1 步：确认字段与口径（先问，别猜）

读到文件后先探测字段，把结果告诉用户并让其确认：

- 找到了哪些列、映射到哪个角色（名称/数量/金额/时间/分类/状态/付款方式）
- 时间取自哪里（商品表自带 or 订单表关联）
- **不要问是否剔除支付方式**——默认就是全渠道，这是对的
- 窗口天数（默认 60）、基准期天数（默认 28）、门槛件数（默认 8）

字段识别不了时用 `--col-*` 显式指定，**不要猜列**——猜错会静默算错。

### 第 2 步：跑计算

```bash
/usr/bin/python3 scripts/diagnose.py \
  --goods  <商品明细1.csv> [<商品明细2.csv> ...] \
  --order  <订单表1.csv>   [<订单表2.csv> ...]   \
  --out    ./out \
  --client "客户名"
```

**不要加 `--exclude-pay`**（默认全渠道）。

多个月份分文件时并列传多个，脚本按列交集纵向拼接。

常用参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--days` | 60 | 分析窗口天数 |
| `--baseline-days` | 28 | 基准期天数（从上架日或窗口起点算） |
| `--recent-days` | 7 | 近一期天数 |
| `--min-base-qty` | 8 | 基准期最少件数，低于此判「数据不足」 |
| `--offline-weeks` | 2 | 连续多少个自然周无销量即判「已下架」 |
| `--star-share` | 5 | 销量明星：近一周占比高于此值（%） |
| `--drop-cut` | 30 | 可下架 / 准备下架（跌幅路径）的最低跌幅（%） |
| `--drop-risk` | 20 | 主力品下滑预警的最低跌幅（%） |
| `--tiny-share` | 1.0 | 单周金额贡献门槛（%）。近 2 周每周都低于此值 + 排名都在下四分位 → 准备下架（不看跌幅） |
| `--lq` | 0.25 | 下四分位界限（0—1），分位 ≤ 此值算垫底 |
| `--top-pct` | 0.30 | 前段界限（0—1），分位 ≥ 1-此值算前段 |
| `--evergreen-share` | 1 | 长青款：每周有成交且全窗口销售占比高于此值（%） |
| `--evergreen-cap` | 关 | 关闭长青款标签 |
| `--evergreen-downgrade` | 关 | 长青款命中下架阈值时强制降级为观察（旧行为） |
| `--new-days` | 30 | 新品：首次成交距窗口末不超过此天数 |
| `--judge-season` | 关 | 已废弃，保留仅为兼容旧脚本（季节款现在默认参与判定） |
| `--keep-non-sale` | 关 | 保留运费/补差价等非售卖行 |
| `--sheet` | 第1个 | Excel 工作表名 |
| `--col-name` `--col-qty` `--col-amt` `--col-date` `--col-cat` `--col-price` `--col-status` `--col-pay` `--col-order` | 自动 | 覆盖列映射 |

## 判定规则（核心，改动需谨慎）

按顺序命中即止：

| # | 条件 | 结论 | 动作 |
|---|---|---|---|
| 0 | 商品名/分类含**具体节日**关键词 | **节令商品·可归档** | 节日短期产品，不参与下架判定；节后统一归档 |
| 1 | 连续 **≥2 个自然周（≥14 天）无任何销量** | **已下架** | 视为已下架，**不再进入**下架/观察判定；确认链接是否已下、还挂着就去清 |
| 2 | 跌幅 **≥ 30%** 且 **近 3 周排名都在下四分位** | **可以下架** | 跌了三周还一直在垫底区，已不是生意的一部分；直接下架 |
| 3 | **近 2 周排名都在下四分位**，且满足二者之一：<br>① 跌幅 **≥ 30%**<br>② 近 2 周**每周**的单周金额贡献都 **< 1%**（该商品当周销售额 ÷ 当周全店销售额） | **需消耗原料·准备下架** | 已在垫底区但不满三周；不再补货，清完库存后下架。**②这条路不看跌幅**——量已经小到可忽略，涨跌都该清 |
| 4 | 跌幅 **> 20%** 且 **近 2 周排名都在前 30%** | **主力品下滑预警** | 还是主力但在退潮，不能砍；同步推新品承接 |
| 5 | 跌幅 ≥ 15%（未命中上面任一条） | 观察 | 再等一周，避免误判波动 |

### 🔴 规则 3 为什么有两条路（2026-11-06 Mirror 追加）

只看跌幅会漏掉一类该清的货：**体量本来就极小、每周都垫底，但因为基数太低，跌幅压根算不出来**。卖 3 件变 2 件是 −33%，卖 1 件变 1 件是 **0%**——两者都该清，但后者永远进不了跌幅门槛。

所以第二条路只问两个问题：**「你是不是每周都在垫底区」+「你到底占多少」**。占比 < 1% 意味着全店每 100 块里它连 1 块都不到，这种商品占着菜单位、原料 SKU 和出品人力，但产出几乎为零。**这条路刻意不设跌幅**——平稳甚至微涨也照判（某蛋糕品牌A本期就有一个 +2.9% 的进了名单）。

两条路要分开讲，因为处理节奏不同：
- **跌幅路径**：原来是主力、现在掉下来 → 值得问一句「为什么掉了」，可能是口味、季节、竞品或断货
- **量小路径**：一直就这么小 → 不用问原因，它就是不该继续占位

实现上判 `判定依据` 字段区分哪种触发，证据卡按实际触发的那条展示（跌幅路径显示跌幅，量小路径只显示周金额贡献），不要一律讲跌幅。

### 🔴 「排名分位」怎么算（2026-11-06 改为排名制）

**每周**把**当周有成交的商品**按销售额从高到低排名，算这个商品落在第几百分位：
- **分位越低 = 卖得越差**
- **≤ 25% = 下四分位**（垫底那四分之一）
- **≥ 70% = 前 30%**
- 当周零成交 → 记为 0（视为最差）

**为什么必须只在「当周有成交」的商品里排名**：某蛋糕品牌A 407 个商品，每周只有 110—160 个有成交，剩下 250—300 个当周零销。若按全部 407 个排名，下四分位会被零销商品占满 —— 只要卖出任何金额就进不了下四分位，规则失效。只在有成交的商品中排名，比的才是「同期谁卖得比你好」。

**为什么用排名而不是固定金额线**：各周有成交的商品数不同（某蛋糕品牌A 96—159 个），¥100/周 在 96 个商品的周是中等偏上，在 159 个商品的周可能是垫底。绝对金额线会随周漂移。

**规则 2 天然包含规则 3**（近 3 周都在垫底 ⇒ 近 2 周当然也在），所以**先判 3 周、再判 2 周**，两者不重叠。

### 长青款（只是标签，不再强制降级）

窗口内**每周都有成交** + 全窗口销售额占全店 **> 1%** → 标「长青款」。

换成排名规则后，**长期卖得好的商品天然进不了下四分位**，所以不会再被误判下架；如果它真在退潮（仍在前 30% 但跌幅超 20%），会落到「主力品下滑预警」——比降级成「观察」更有用，因为它直接告诉你该准备接棒了。

**历史背景**：2026-11-06 之前用的是「跌幅 + 近一周销售占比」两点对比，某蛋糕品牌A「招牌口味·芭乐布蕾爆浆蛋糕」（¥15,013，407 个商品中排第 6，9/9 周连续在售）因 -59.3% + 占比 1.68% 被判「可以下架」，客户指出它是长青品只是近期波动（芭乐过季）。当时临时加了「长青款强制降级为观察」；改成排名制后该保护已非必要，默认只作标签。如需旧行为加 `--evergreen-downgrade`。

参数：`--evergreen-share`（默认 1）、`--evergreen-cap`（关闭标签）、`--evergreen-downgrade`（恢复强制降级）。

**节令只指具体节日**：中秋 / 月饼 / 情人节 / 万圣节 / 圣诞 / 元旦 / 跨年 / 春节 / 年货 / 元宵 / 端午 / 粽子 / 七夕 / 母亲节 / 父亲节 / 教师节 / 国庆 / 重阳 / 腊八 / 儿童节 / 清明 / 平安夜 / 除夕 等。**全部归入同一个「节令商品·可归档」，不再细分「不判定 / 已到期」。**

**季节描述不算节令，照常参与判定**：`秋冬限定` / `季节限定` / `时令` / `夏日` / `秋季` 这类只描述季节、不含具体节日的，**按普通商品判定**——它们是当季主推，卖不动恰恰是最该提醒的。IP 联名（`汪汪限定` / `TAGI 限定`）同样照常判定。

**规则 0、1 优先**：命中节令或连续两周零成交的商品，即使跌幅 −100%，也**不会**出现在「可以下架」或「观察」里。

**两个「分区标签」不参与判定，只做结构观察**（与判定并列显示，可同时命中）：

| 分区 | 定义 | 用途 |
|---|---|---|
| **销量明星** | 近一周销售额贡献占比 **> 5%** | 当前撑量的主力；下架决策时优先保 |
| **新品** | 首次成交距窗口末 **≤ 30 天**且仍在售（节令商品不重复计入） | 看新品接棒：上得快不快、有没有量 |
| **长青款** | 每周都有成交 + 全窗口销售占比 **> 1%** | 见上方保护规则；命中时判定自动降级为观察 |

**跌幅定义**：从商品上架日（或窗口起点）起 `baseline_days` 天为基准期，与最近 `recent_days` 天比较，**均按日均**（消除周天数不一致）。
`跌幅 = (近一期日均 − 基准期日均) ÷ 基准期日均`。

**近一周销售贡献占比** = 该商品最近 7 天销售额 ÷ 全店同期销售额。

## 在售状态怎么判断

源表通常没有「上架/下架」字段，用**连续无成交周数**代理：

- 连续 **≥ 2 个自然周（≥14 天）零销量**（或整个窗口零成交）→ **已下架**
- 否则 → **在售**

回到在售状态需要重新出单。`下架原因` 字段会写明是「连续 N 周无销量」还是「整个窗口无成交」，报告表格的「距末售」列会直接显示这句话。

## 已知必踩的坑

1. **「商品数量」对定制/虚拟商品可能是金额错位**：某些店铺的「来图定制」行会写成 `单价=1、数量=订单金额`。不剔会让该品类件数虚高上百倍。脚本默认剔 `来图定制|运费|补差价|蜡烛|刀叉|餐具|收藏福利`，并按 99.9 分位截断异常数量。
2. **同名商品因首尾空格被拆成两行**：聚合前必须 `strip` + 压缩连续空白，否则趋势被劈开。
3. **首末周天数不足 7 天**：一律用日均比较，绝不直接比绝对件数。
4. **pandas 的 NaN 在 `if` 里是真值**：混合字典建 DataFrame 时缺失键会填 NaN，布尔列必须显式 `.fillna(False).astype(bool)`，否则整表误判。
5. **低基数商品会淹没结论**：基准期只卖 3—5 件的商品，跌幅再大也是噪声。用 `--min-base-qty` 抬门槛，报告里也能按基准期件数筛。
6. **渠道口径先对齐**：客户若在团购平台（抖音券/美团券）也有同款，但那部分商品行与门店 SKU 不完全对应，先问清是否剔除，否则「销量暴跌」可能只是渠道迁移。

## 报告怎么读给客户听

不要只念数字。建议顺序：

1. **先给结论数量**：可以下架 N 个、准备下架 M 个、主力品下滑预警 K 个，可释放月销售额 ¥X
2. **点 2—3 个具体商品**：名称 + 跌幅 + 近一周占比 + 月缺口，说明「为什么砍它」
3. **单独说已下架链接**：连续两周零成交的有多少个，问客户「是下架了还是断货」——链接还挂着就是白占流量
4. **先夸再提结构问题**：先说销量明星是哪几个、新品接棒得怎么样，再说长尾占比过高（如 70% 的商品月销不足 8 件）——这不是下架几个 SKU 能解决的，是货盘结构问题
5. **节令商品一句话带过**：中秋月饼这类跌幅 -90% 不是产品问题，不用展开

边界情形与规则推导见 `references/rules.md`。
