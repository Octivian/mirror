## 二、更新流程（6 步）

1. **触发**：Mirror 口头发起「更新 XX 的客户档案」。
2. **扫描**：检查桌面 `C:\Users\admin\Desktop\<客户名>\` 中较上次更新后**新增或修改过**的文件（按修改时间比对）。
3. **判断**：识别哪些内容对档案有价值，重点采纳维度：
   - 经营数据（营收 / 渠道 / 成本 / 会员 / 储值）
   - 合作进展（阶段变化、交付物、双方分工、组织决策人）
   - 产品与商品结构（品类、SKU、规格、定价、上新）
   - 用户洞察（画像、需求缺口、口碑）
   - 竞品与市场格局
4. **确认**：先列「拟采纳要点」+「存疑/暂不采纳」清单，与 Mirror 确认后再写入。**不得自行拍板落盘。**
5. **更新**：改本地 md（每条数据标注来源 + 页码；章节末标注更新日期）→ 覆盖云盘对应文档。
6. **归档**：把本次引用的源文件复制到 `D:\工作\<客户>\客户档案\源数据\`，保持原始文件名。

## 三、写作约定

- 每个数字都要能回答「来自哪份文件 / 哪一页 / 哪个口径」。
- 数据对不上时写入「待确认与存疑项」章节，**不在正文里抹平**。
- 存疑项闭环后标注 ✅ 并保留记录，不删除历史。
- 口径冲突（同一指标两处数值不同）→ 两个都列，并标注冲突，不擅自取一个。
- **信源辨别（同类信息取最新）**：客户文件夹里常有多份内容相似度高的材料（如某复合烘焙C的 `问题诊断_20260928_v2` 与 `解决方案沟通会-1011`）。同一类信息**一律以最新时点为准**；两份口径冲突且分不清先后时，**先与 Mirror 确认，不自行取舍**。
- **区分「提案建议」与「已确认事实」**：方案材料中由**我方提出**的机制、分工、考核指标，必须标注为"提案建议（待客户确认）"，不得写成客户已确认的事实。
- **问题定位以可验证的经营事实为准**：诊断优先锚定硬事实链（如"门店面积缩减 → 渠道结构变化"），内部管理层面的归因不写入根因章节。
- **只写事实，不写推断的因果**：凡是档案里出现的结论，都要能指回源文件原句；推断一律显式标注为"推断"或放入存疑项。
